Harness System Flow

当前 Harness 整体流程

Harness 是本地优先的 Codex / Agent 研发闭环控制面。一次任务会从 $harness 或 pnpm workflow:* 进入，经过需求结构化、测试矩阵、编码计划、自动测试、质量验证、Git 收尾记录、MR Summary、部署记录和最终执行归档。

服务泳道

当前 Harness 用多个 JSON-RPC 服务拆开职责：编排服务只推进状态机和持久化记录，分析、计划、测试、部署分别由独立服务负责。

一次 run 的主线

run-workflow.mjs 先检查 /health。如果服务未就绪且没有设置 HARNESS_SKIP_BOOT=1，脚本会启动 pnpm dev:services，再调用 orchestrator 的 runWorkflow。

质量闭环

Harness 的关键不是只跑命令，而是把失败日志变成修复建议，把修复变成重跑证据，再把证据写回 task JSON 和 docs。

自动验证

  • pnpm typecheck 覆盖 TypeScript 类型契约。
  • pnpm test 运行 Vitest 单元测试。
  • pnpm target:build 验证目标产品构建。
  • pnpm target:browser 执行无头浏览器质量门。

失败处理

testing-rpc 输出 ParsedFailure，必须包含 reason、evidence 和 suggestedFix。可修复时进入 fixing -> retesting，超过重试或部署异常则 blocked。

视觉与 E2E

quality-validation 不写死点击路径。Codex 根据本次改动选择截图、语义快照、网络、console、可访问性或 agent-browser 验证，并留下任务相关证据。

常用入口命令

三类任务共享同一条稳定 flow。区别在于前置判断：requirement 强调验收标准，bugfix 强调复现和回归测试，polish 强调影响面与用户可见改进。 

$harness requirement 增加一个工作流运行详情页
$harness bugfix 测试服务日志解析失败
$harness polish 优化前端任务状态展示

pnpm workflow:requirement "<需求>"
pnpm workflow:bugfix "<Bug 或失败日志>"
pnpm workflow:polish "<优化目标>"
pnpm workflow:git review -- --run-id <run-id>

pnpm verify
pnpm health
docker compose up --build

审计产物

一次流程结束后，结构化记录和人工可读文档必须互相对得上。这里是排查“跑到哪一步了”和“为什么失败”的第一现场。
